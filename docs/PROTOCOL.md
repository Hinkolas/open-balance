# Open Balance – protocol v1

Status: draft, 2026-11-02. This document is the contract between the server
and every client (iOS now, Android and Windows later). If two clients reduce
the same ledger differently, members see different balances, so every rule
here is normative. Change `spec/vectors/*.json` together with this file, then
the implementations.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Overview

A **group** is an append-only, end-to-end encrypted **ledger** of events kept
on a **server**. The server orders events (assigns `seq`), authenticates the
members' keys and stores ciphertext. It never sees names, amounts or event
types. Clients download the ledger, decrypt it, verify signatures and replay
it into the current state (members, payments, balances, history).

```
epoch secret S_e (32 bytes; epoch e = 0, 1, 2, …)
  └─ K_e = HKDF(S_e)            encrypts the events of epoch e (ChaCha20-Poly1305)
member key (Ed25519, one per device of a member, per group)
  ├─ signs every event          clients verify: who wrote what
  └─ signs every request        server verifies: who may read/write
box key (X25519, one per device, pending invite and recovery key)
  └─ receives epoch secrets     sealed to it, in the ledger and on the server
invite key (Ed25519, one-time)  lets a new device register its member key
recovery key (Ed25519, one per group, kept offline by the admin)
  └─ replaces the admin's devices after they are all lost
```

In short: **one secret per epoch for reading, one or more keys per member for
writing.** A member can be a person or a company whose people share it; every
device of the member writes as that member.

| Key | Held by | Role |
|---|---|---|
| Epoch secrets `S_e` | every device of every member | read: decrypt the ledger |
| Member key | one device of a member (a member may have several) | write: sign events and server requests; identifies the member |
| Box key | each device, pending invite and the recovery key | receive epoch secrets |
| Invite key | one pending device, once | join: swap itself for a member key |
| Recovery key | the admin, outside the app (a password manager) | recover: register a new admin device, removing the old ones |

When a device is removed, a new **epoch** starts: a fresh secret, sealed to
the box key of every remaining reader (§7.2). The removed device keeps the
old secrets and can read what was written before, but nothing written after,
even with the server's help.

`K_e` is symmetric, so a holder of `S_e` could also produce ciphertext. That
grants no write access: the server only accepts appends signed by a
registered member key, and clients only apply events whose inner signature
matches the author's member key.

Keys form a tree. The admin's key is the root of a group: the admin adds
members, and each member's first device claims its seat with a one-time
invite. After that only the member itself adds further devices. Every device
generates its own key and no key ever leaves the device that made it, except
the recovery key, which the admin keeps outside the app.

The server owner's `ADMIN_TOKEN` approves the creation of groups and nothing
else: it gives no key of any group and no way to read one (§5.4).

What the server learns: group ids, the member public keys of a group and their
role, which key wrote which event and when, blob sizes (padded), IP addresses.
What it cannot do: read events, write valid events (it has no `K_e`),
forge a member's events (no private keys), reorder or rewrite history without
clients noticing (hash chain, §6.4). It can withhold the newest events.
Invite and recovery links hold no epoch secret; the server keeps keyrings
sealed to their box keys (§3.5) and hands them out only on a claim or a
recovery.

## 2. Primitives and encodings

| Purpose | Algorithm |
|---|---|
| Key derivation | HKDF-SHA256 (RFC 5869) |
| Event encryption | ChaCha20-Poly1305 IETF, 96-bit random nonce, 128-bit tag (RFC 8439) |
| Key agreement | X25519 (RFC 7748) |
| Signatures | Ed25519 (RFC 8032), pure, 64-byte signatures |
| Hashing | SHA-256 |

- **UUIDs** are RFC 9562. Ids created by clients are UUIDv7. In JSON they are
  lowercase hyphenated strings; in binary contexts (`groupId(16)`) the 16 raw
  bytes.
- **base64url** is RFC 4648 §5 without padding.
- **Public keys** are the 32 raw Ed25519 bytes, base64url in JSON and headers.
- **Integers** in JSON are plain numbers within ±(2^53 − 1).
- **Strings** are UTF-8, NFC normalized by the writer. Lengths below count
  Unicode scalar values.
- `‖` is byte concatenation. String literals are their UTF-8 bytes without a
  terminator. `u32be`/`u64be` are big-endian unsigned integers.

Ed25519 signatures from CryptoKit are randomized; verification is standard.
Test vectors therefore check verification, not signature bytes.

## 3. Keys

### 3.1 Epoch secrets

`S_0` is 32 bytes from a CSPRNG, generated by the admin's device when the
group is created. Each new epoch (§7.2) gets a new 32-byte random secret from
the device that starts it. Epoch secrets never leave clients except sealed to
a box key (§3.5). Clients keep every epoch secret they have: replaying the
ledger needs all of them.

```
K_e = HKDF-SHA256(ikm = S_e, salt = groupId(16), info = "open-balance/v1/enc" ‖ u32be(e), L = 32)
```

### 3.2 Member keys

Every device of a member has its own Ed25519 key pair for this group,
generated on that device. All keys of a member are equal: each writes as the
member. A member gets its first key by claiming its seat and every further key
through a device invite (§7.3).

Clients MUST keep epoch secrets, member private keys and invite seeds on
the device: not synced, not in backups, not exportable (iOS: Keychain with
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; Android: sealed with an
Android Keystore key in no-backup storage). A lost device stays lost: another
device of the member, or the admin, removes its key (§7.3), and a new device
joins with a device invite. If a member has lost every device, the admin
resets the member (§5.4 step 7).

### 3.3 Invite keys

An invite key is an Ed25519 key pair derived from a 32-byte random seed `I`
(the seed is the RFC 8032 private key). The admin creates one per unclaimed
member (its first device); a claimed member creates one for each further
device of its own. Each is valid for exactly one claim.

### 3.4 Recovery key

A recovery key is an Ed25519 key pair derived from a 32-byte random seed `R`.
The admin's device creates it with the group and whenever the admin asks for a
new one, shows it once as a recovery link (§4) for the admin to keep in a
password manager, and then forgets `R`: clients MUST NOT store it. Its public
key is in the ledger (§7.1, §7.2) and in the server's key registry (role
`recovery`). With it, a new device takes over the admin's seat (§7.3
`member.recovered`):

```
recoverySig = Ed25519(R, "open-balance/v1/recover" ‖ groupId(16) ‖ key(32))
```

The recovery link holds `R`. With it the server hands out the recovery
key's keyring, and later epoch secrets are sealed to the recovery key's box
key (§3.5): whoever has the link can read the group and act as its admin.

### 3.5 Box keys and sealing

Every seed in a group (a device's member key seed, an invite seed `I`, the
recovery seed `R`) also yields an X25519 **box key**:

```
box private key = HKDF-SHA256(ikm = seed(32), salt = "", info = "open-balance/v1/box", L = 32)
```

used as an RFC 7748 X25519 private key (clamped as RFC 7748 says). Its
public key is published in the ledger next to the Ed25519 key of the same
seed (§7). Secrets for a box key `P` are sealed:

```
seal(P, label, m):
  e   = fresh X25519 key pair
  z   = X25519(e, P)                       MUST NOT be all zero
  k   = HKDF-SHA256(ikm = z, salt = groupId(16), info = label ‖ e_pub(32) ‖ P(32), L = 32)
  out = e_pub(32) ‖ ChaCha20-Poly1305(k, nonce = 12 zero bytes, m, aad = "")
```

A fresh `e` per seal makes every `k` unique, so the fixed nonce is safe.

| What | label | m |
|---|---|---|
| Epoch secret in `group.epoch_started` | `"open-balance/v1/epoch"` | `u32be(e) ‖ S_e` (36 bytes, sealed 84) |
| Keyring of an invite or the recovery key | `"open-balance/v1/keyring"` | `S_0 ‖ S_1 ‖ … ‖ S_e`, every secret so far |

The reader MUST check that a sealed epoch secret names the epoch it is
announced for and that a keyring is a non-empty multiple of 32 bytes.

## 4. Links

### 4.1 Invite link

The admin shows a member's invite, and a member's device shows a device
invite for its own member, as a QR code of the same URL:

```
openbalance://join?v=1&s=<server>&g=<groupId>&m=<memberId>#i=<I>
```

| Param | Value |
|---|---|
| `v` | protocol version, `1` |
| `s` | server base URL, percent-encoded, `https://` (plain `http://` only in debug builds) |
| `g` | group id |
| `m` | member id this invite is for |
| `i` | base64url invite seed `I` |

The seed sits in the fragment so a link pasted into a browser never sends it
anywhere. The link holds no epoch secret: the server releases the invite's
keyring (§3.5) only to whoever claims the invite. Anyone holding the link can
claim the seat until it is claimed; afterwards it is useless (the server
rejects the invite key).

### 4.2 Recovery link

```
openbalance://recover?v=1&s=<server>&g=<groupId>&m=<adminId>#r=<R>
```

`v`, `s` and `g` as in §4.1; `m` is the admin's member id; `r` is the
base64url recovery seed `R` (§3.4). It works until the admin replaces the
recovery key.

### 4.3 Creation link

The server owner gives the person who will create and administer a group:

```
openbalance://create?v=1&s=<server>#c=<code>
```

`c` is a creation code (§5.3), used up by the first group created with it.

## 5. Server API

JSON over HTTPS. Base path `/v1`. Errors are `{"error": {"code": "...", "message": "..."}}`
with a matching HTTP status.

### 5.1 Request authentication

Member and invite requests carry:

```
Authorization: OB1 key=<base64url public key>, ts=<unix seconds>, sig=<base64url signature>
```

```
sig = Ed25519(key, "open-balance/v1/req\n" ‖ METHOD ‖ "\n" ‖ path-and-query ‖ "\n"
                   ‖ ts ‖ "\n" ‖ lowercase hex SHA-256(body))
```

`path-and-query` is exactly as sent (e.g. `/v1/groups/…/events?after=41`).
An empty body hashes the empty string. The server MUST reject a timestamp more
than 300 s from its clock and a key that is not registered for the group in
the path with the required role and status. Replays inside the window are
harmless: reads are reads and appends are idempotent.

Server-owner requests carry `Authorization: Bearer <ADMIN_TOKEN>` (the server
owner's secret, an environment value). Compared in constant time. Creating a
group also accepts `Authorization: Bearer <creation code>` (§5.3); the server
stores only the SHA-256 of a code.

### 5.2 Key registry (server side)

Per group the server keeps `(publicKey, role, status, seat)`, and for invites
the key that created it and the role it grants:

| role | status | may |
|---|---|---|
| `admin` | `active` | everything a member may, plus remove any key, revoke any invite, create invites that grant `admin`, replace the recovery key |
| `member` | `active` | read and append events, read stream, create invites that grant `member`, revoke invites it created, remove keys of its own seat |
| `recovery` | `active` | recover only |
| `invite` | `pending` | claim only |
| any | `claimed`, `revoked`, `removed` | nothing |

A **seat** is the server's view of a member, which it can't see otherwise:
the admin key from group creation and every key from an invite that grants
`admin` or comes from the recovery key share the admin's seat; a key from an
invite a member created shares that member's seat; a key from an invite the
admin created that grants `member` starts a new seat (a new member, or a
member the admin reset). Seats let a member remove its own devices and
nobody else's.

The server can't tell members apart in the ledger, so it lets any member
create invites; which member an invite belongs to and who may create it is
decided in the ledger (§7.3). A key registered through an invite the ledger
doesn't back can read, as anyone holding a QR code could, but its events are
invalid.

When a key is removed, the pending invites it created are revoked with it.

v1 has exactly one admin per group: the creator, on each of its devices.
Removing members from a group entirely and more admins are on the roadmap.

### 5.3 Endpoints

| Method and path | Auth | Body → response |
|---|---|---|
| `GET /v1/info` | none | → `{name, version, protocols: [1]}` |
| `POST /v1/groups` | owner or creation code | `{groupId, adminKey, recoveryKey, recoveryKeyring}` → 201. Registers the group, its admin key and its recovery key with its keyring. Uses up the creation code. |
| `POST /v1/admin/creation-codes` | owner | `{expiresInHours?}` → 201 `{id, code, expiresAt}`. A one-time code that lets its holder create one group. `expiresInHours` 1–720, default 168. |
| `GET /v1/admin/creation-codes` | owner | → `{codes: [{id, createdAt, expiresAt, usedAt, groupId}]}` (never the code) |
| `DELETE /v1/admin/creation-codes/{id}` | owner | → 204. Withdraws an unused code. |
| `GET /v1/admin/groups` | owner | → `{groups: [{groupId, createdAt, lastWriteAt, events, bytes}]}` |
| `DELETE /v1/admin/groups/{g}` | owner | → 204. Deletes the group and all events. |
| `POST /v1/groups/{g}/invites` | member | `{inviteKey, role?, keyring}` → 201. `role` is what the claimed key gets: `member` (default) or `admin` (admin callers only, for the admin's own devices). |
| `DELETE /v1/groups/{g}/invites/{inviteKey}` | member | → 204 (pending → revoked). The admin may revoke any invite, a member only those it created. |
| `POST /v1/groups/{g}/claim` | invite | `{memberKey, proof}` → 200 `{keyring}`. Atomically: invite pending → claimed, memberKey registered with the invite's role, seat and keyring, `active`. |
| `DELETE /v1/groups/{g}/keys/{key}` | member | → 204. An `admin` or `member` key → `removed`, and its pending invites → `revoked`. The admin may remove any such key, a member only keys of its own seat. |
| `PUT /v1/groups/{g}/recovery` | admin | `{recoveryKey, keyring}` → 204. The current recovery key → `removed`, `recoveryKey` registered as `recovery`. |
| `POST /v1/groups/{g}/recover` | recovery | `{memberKey, proof}` → 200 `{keyring}`. Atomically: every key of the admin's seat → `removed` and their pending invites → `revoked`; memberKey registered as `admin` in the admin's seat, with the recovery key's keyring. The recovery key stays. |
| `GET /v1/groups/{g}/keyring` | member | → `{keyring}`, the keyring the caller's key got with its claim or recovery, for a client that lost the response. 404 for keys that got none. |
| `POST /v1/groups/{g}/events` | member | `{events: [{id, blob}]}` → `{events: [{id, seq}]}` |
| `GET /v1/groups/{g}/events?after=<seq>&limit=<n>` | member | → `{events: [{seq, id, blob, authorKey, receivedAt}], head}` |
| `GET /v1/groups/{g}/stream` | member | Server-sent events, `event: head` / `data: {"seq": n}` on every append and every 30 s |
| `GET /healthz`, `GET /readyz` | none | probes |

- `proof = Ed25519(memberKey, "open-balance/v1/claim" ‖ groupId(16) ‖ signingKey(32))`
  proves the claimer holds the member private key. `signingKey` is the key
  the request is signed with: the invite key for `claim`, the recovery key
  for `recover`.
- A **creation code** is 32 random bytes, base64url. The server stores its
  SHA-256, expiry and, once used, the group it created. An expired, used or
  withdrawn code is rejected with 401.
- Keys are unique per group: registering a key the group has seen before, in
  any role and status, fails with 409.
- A **keyring** is a sealed keyring (§3.5) for the box key of the invite or
  recovery key it comes with, base64url, at most 64 KiB. The server stores it
  as received and never reads it.
- **Append** assigns consecutive `seq` values starting at 1 per group, in
  request order, in one transaction. An `id` that already exists in the group
  returns its existing `seq` and is not stored twice. `blob` is base64url,
  a version 2 blob (§6.1) of at most 64 KiB decoded; at most 100 events per
  request.
- **Read** returns events with `seq > after` in ascending order, `limit`
  default 500, max 1000. `head` is the group's current highest `seq`.
- `blob`, `id` and `authorKey` are stored as received; the server never parses
  the blob.
- Quotas (configurable): events per group, bytes per group, appends per
  minute per key. Exceeding them returns 429.

### 5.4 Group flows

0. **Approve** (server owner): `POST /v1/admin/creation-codes` → give the
   creation link (§4.3) to the person who will create the group. The server
   owner holds no key of the group and can't read it. A server owner who
   wants a group of their own creates it with `ADMIN_TOKEN` directly; that
   makes them the admin of that group only.
1. **Create** (the future admin's device, with a creation code or
   `ADMIN_TOKEN`): generate `groupId` (UUIDv7), `S_0`, member id, admin key
   and recovery seed `R` → `POST /v1/groups` with a keyring `[S_0]` sealed to
   the recovery box key → append `group.created` (§7.1) signed by the admin
   key → show the recovery link (§4.2) once, then forget `R`.
2. **Add member** (admin): generate member id and invite seed `I` →
   `POST …/invites {inviteKey, keyring}` with every epoch secret so far sealed
   to the invite's box key → append `member.added` → show the QR (§4.1).
3. **Join** (new member): scan → generate member key →
   `POST …/claim` signed with the invite key → open the keyring with the
   invite's box key → read the ledger (epochs started since the invite was
   made are sealed to the invite's box key, §7.2) → append `member.claimed`
   (§7.3) signed with the new member key. A client that lost the claim
   response gets the keyring again with `GET …/keyring`.
4. **Lost QR** (admin): `DELETE …/invites/{old}`, then like step 2 with
   `member.invite_renewed` instead of `member.added`.
5. **Add a device** (any device of a claimed member, for its own member):
   generate invite seed `I` → `POST …/invites {inviteKey, role, keyring}`
   (`admin` if the member is the admin) → append `member.device_invited` → show the QR
   (§4.1). The new device scans, claims like step 3 and appends
   `member.device_claimed` instead of `member.claimed`. A pending device
   invite is withdrawn with `DELETE …/invites/{key}` and
   `member.device_invite_revoked`.
6. **Remove a device** (another device of the member, or the admin): append
   `member.device_removed`, then `DELETE …/keys/{key}`, then start a new
   epoch (step 10). The removed device can't read or write any more, and
   can't read what is written after the new epoch even with the server's
   help.
7. **Reset a member** (admin, when the member lost every device): for each of
   its keys step 6, then like step 4 with a new invite for the member's new
   first device. The member keeps its id, name, payments and balance.
8. **Recover** (the admin lost every device): open the recovery link →
   generate a member key → `POST …/recover` signed with the recovery key →
   open the keyring with the recovery box key → read the ledger → append
   `member.recovered` (§7.3) → start a new epoch (step 10). Pending invites
   of the old admin devices no longer work; the admin renews them (step 4).
9. **New recovery key** (admin): generate `R` → `PUT …/recovery` with every
   epoch secret so far sealed to the new recovery box key → append
   `group.recovery_changed` → start a new epoch (step 10) → show the new
   recovery link once. The old link stops working, and can't read what is
   written after the new epoch.
10. **New epoch** (whenever one is due, §7.2): generate `S_e+1` → append
    `group.epoch_started` sealing it to every reader, in the same request as
    the event that made it due when possible. If it turns out invalid (the
    readers changed first) and an epoch is still due, the device that made
    it due, or any device of the admin, starts another. A client holding
    unsent events sealed with an older epoch seals them again with the
    current one before appending; its own events that were appended sealed
    with an older epoch are invalid (`stale_epoch`, §8.1), so it writes them
    again as new events.

## 6. Event envelope

### 6.1 Blob

```
blob      = 0x02 ‖ u32be(epoch) ‖ nonce(12) ‖ ChaCha20-Poly1305(K_epoch, nonce, plaintext, aad)
aad       = "open-balance/v1/event" ‖ groupId(16) ‖ eventId(16) ‖ u32be(epoch)
plaintext = u32be(len(body)) ‖ body ‖ signature(64) ‖ zero padding
signature = Ed25519(authorKey, "open-balance/v1/sig" ‖ groupId(16) ‖ eventId(16) ‖ body)
```

The plaintext is padded with zero bytes to the next multiple of 256 bytes.
The signature is over the exact `body` bytes received; readers MUST NOT
re-serialize before verifying. `eventId` is the `id` sent to the server.
`epoch` is the epoch the writer sealed with: the current epoch in its view
(§7.2).

### 6.2 Body

`body` is a UTF-8 JSON object:

```json
{
  "v": 1,
  "type": "payment.created",
  "author": "0192f0c4-…",
  "at": "2026-11-01T14:03:11Z",
  "seen": { "seq": 41, "chain": "base64url 32 bytes" },
  "data": { }
}
```

| Field | Meaning |
|---|---|
| `v` | protocol version, `1` |
| `type` | event type, §7 |
| `author` | member id of the writer; the signature must verify with that member's key (§8.2) |
| `at` | the writer's clock, RFC 3339 UTC. Display only, never used for ordering |
| `seen` | the newest event the writer had applied, §6.4. `{"seq": 0, "chain": <32 zero bytes>}` if none |
| `data` | type specific |

Unknown fields MUST be ignored (forward compatibility). Unknown `type`s are
kept in the history as "unsupported" and otherwise ignored.

### 6.3 Order

The ledger order is the server `seq`, ascending. Nothing else (not `at`, not
UUIDv7 time) orders events.

### 6.4 Hash chain

Every client computes over the server order:

```
chain_0 = 32 zero bytes
chain_n = SHA-256("open-balance/v1/chain" ‖ chain_{n-1} ‖ u64be(n) ‖ eventId_n(16) ‖ SHA-256(blob_n))
```

A client MUST stop applying events and show the group as **inconsistent** if:

- the `seq` values it receives are not exactly 1, 2, 3, … without gaps, or
- an event's `seen.seq` is less than its own `seq` and the client's
  `chain_{seen.seq}` differs from `seen.chain`.

A server that shows different histories to different members is detected as
soon as a member writes after seeing the forked history.

## 7. Event types

All ids in `data` are UUID strings. `name`: 1–100 characters, `title`: 1–200,
`note`: 0–2000. Amounts are integers in minor units of the group currency,
`1 ≤ amount ≤ 10^15`.

### 7.1 `group.created`

```json
{ "name": "Italien 2026", "currency": "EUR",
  "admin": { "id": "…", "name": "Jonas", "key": "…", "boxKey": "…" },
  "recoveryKey": "…", "recoveryBoxKey": "…" }
```

MUST be the event with `seq = 1` and the only `group.created`. `currency` is
an ISO 4217 code and fixed for the life of the group; its minor-unit exponent
comes from ISO 4217 (EUR 2, JPY 0). `author` MUST equal `admin.id`; the event
is signed with `admin.key`. The admin is a claimed member from the start.
`recoveryKey` is the public recovery key (§3.4), different from `admin.key`.
`admin.boxKey` and `recoveryBoxKey` are the box keys (§3.5) of the admin's
device and of the recovery key. It MUST be sealed with epoch 0.

If `seq = 1` is not a valid `group.created`, the whole group is invalid.

### 7.2 `group.updated`, `group.recovery_changed`, `group.epoch_started`

`group.updated`: `{ "name": "…" }`. Admin only.

`group.recovery_changed`: `{ "recoveryKey": "…", "recoveryBoxKey": "…" }`.
Admin only. Both MUST be new keys; they replace the current recovery key and
its box key.

`group.epoch_started` starts epoch `n`:

```json
{ "epoch": 2, "keys": [ { "key": "<box key>", "secret": "<seal(key, \"open-balance/v1/epoch\", u32be(2) ‖ S_2)>" } ] }
```

Any claimed member. `epoch` MUST be the current epoch + 1 and `keys` MUST
hold every **reader** exactly once and nothing else, each `secret` 84 bytes
(`invalid_data` otherwise). Then `n` is the current epoch. The event itself
is sealed with the previous epoch, so every reader can open it; each finds
its own entry and opens it (§3.5). A reader whose entry doesn't open, or
names another epoch, can't read the events that follow.

The **readers** are the box keys of: every key of every claimed member; the
current invite of every unclaimed member that has one; every pending device
invite; the recovery key.

The current epoch is 0 at the start. A **new epoch is due** after a valid
`member.device_removed`, `member.recovered` or `group.recovery_changed`, and
no longer after a valid `group.epoch_started` (§5.4 step 10). Clients only
start epochs when one is due; others are valid but needless.

### 7.3 Members

| Type | data | Who |
|---|---|---|
| `member.added` | `{ "id", "name", "inviteKey", "inviteBoxKey" }` | admin |
| `member.invite_renewed` | `{ "id", "inviteKey", "inviteBoxKey" }` | admin; member must be unclaimed |
| `member.claimed` | `{ "id", "key", "boxKey", "inviteSig" }` | the member itself, see below |
| `member.updated` | `{ "id", "name" }` | admin or the member itself |
| `member.device_invited` | `{ "id", "inviteKey", "inviteBoxKey" }` | the member itself |
| `member.device_claimed` | `{ "id", "key", "boxKey", "inviteKey", "inviteSig" }` | the member itself, see below |
| `member.device_invite_revoked` | `{ "id", "inviteKey" }` | the member itself or admin |
| `member.device_removed` | `{ "id", "key" }` | the member itself or admin |
| `member.recovered` | `{ "id", "key", "boxKey", "recoverySig" }` | the admin, see below |

A member is **claimed** while it has at least one key. Every key an event
introduces (`admin.key`, `admin.boxKey`, `recoveryKey`, `recoveryBoxKey`,
`inviteKey`, `inviteBoxKey`, `key`, `boxKey`) MUST be 32 bytes and new: it
must not have appeared in any earlier valid event of the group, in any role
(`invalid_data`). Keys are never reused, even after they are removed. A box
key belongs to the key it is introduced with (§3.5) and stops being a reader
with it.

`member.added`: `id` must be new.

`member.claimed`: the member must exist and be unclaimed; `author` MUST equal
`id`; the event is signed with `key`; and

```
inviteSig = Ed25519(current inviteKey of the member, "open-balance/v1/claim" ‖ groupId(16) ‖ key(32))
```

must verify. After a valid claim the member is claimed with that key and has
no invite key any more; `member.claimed` events for a claimed member are
invalid (`already_claimed`).

`member.device_invited`: `author` MUST equal `id`, so only a claimed member
invites devices for itself; the admin adds a member's first device through
`member.added` / `member.invite_renewed` only. `inviteKey` MUST be a new key;
it becomes one of the member's **pending device invites**.

`member.device_claimed`: the member must exist (`unknown_target`); `author`
MUST equal `id` (`forbidden`); `key` MUST be a new key (`invalid_data`);
`inviteKey` MUST be one of the member's pending device invites and

```
inviteSig = Ed25519(inviteKey, "open-balance/v1/claim" ‖ groupId(16) ‖ key(32))
```

must verify (`bad_invite_sig` otherwise). The event is signed with `key`.
Then `key` is one more key of the member and the invite is no longer pending.

`member.device_invite_revoked`: the member must exist and `inviteKey` must be
one of its pending device invites (`unknown_target`); it is no longer pending.

`member.device_removed`: the member must exist (`unknown_target`); `author`
MUST equal `id` or be the admin (`forbidden`); `key` MUST be one of the
member's keys (`unknown_target`). The key is no longer the member's: events
it signs later fail with `bad_signature`. If it was the member's last key, the
member is unclaimed again (a seat others record payments for), has no invite
key and no pending device invites; the admin gives it a new invite with
`member.invite_renewed`.

`member.recovered`: `id` MUST be the admin and `author` MUST equal `id`
(`forbidden`); `key` MUST be new (`invalid_data`); the event is signed with
`key`; and

```
recoverySig = Ed25519(current recovery key, "open-balance/v1/recover" ‖ groupId(16) ‖ key(32))
```

must verify (`bad_recovery_sig` otherwise). Then `key` is the admin's only
key: all its earlier keys are removed and its pending device invites are
dropped.

`member.removed` (leaving a group entirely) is reserved for the roadmap.

### 7.4 Payments

A payment has two sides over the same `amount`:

- **in**: who receives the money or value (holders),
- **out**: whom it belongs to (owners).

```json
{
  "id": "…",
  "kind": "income",
  "title": "Projekt Nordlicht, 1. Rate",
  "note": "",
  "date": "2026-10-30",
  "amount": 100000,
  "track": true,
  "in":  { "mode": "exact",   "lines": [ { "member": "A", "amount": 100000 } ] },
  "out": { "mode": "percent", "lines": [ { "member": "A", "amount": 60000, "value": 6000, "rest": true },
                                         { "member": "B", "amount": 40000, "value": 4000 } ] }
}
```

| Field | Meaning |
|---|---|
| `kind` | `income`, `expense` or `settlement`. A label for display and for which form edits it. **Not used by the math.** Unknown values display as `income`. |
| `date` | ISO 8601 calendar date the payment happened, as the user entered it |
| `track` | `true`: only money recorded as arrived counts (§7.5). `false`: counts in full immediately |
| `in`, `out` | split sides |
| `mode` | editing hint for forms: `mixed` (per line an amount, a percentage or the rest), `equal`, `shares`, `exact`, `percent`. Unknown modes reopen as exact amounts |
| `lines[].amount` | **authoritative** resolved amount, ≥ 0 |
| `lines[].value` | editing hint: basis points for `percent`/`mixed` lines entered as a percentage, weight for `shares` |
| `lines[].rest` | editing hint: the line that took whatever was left |

Validation: every side has ≥ 1 line, each member at most once per side, every
member exists, line amounts sum to `amount` on each side. The same member may
appear on both sides. Only `lines[].amount` enters the math; `mode`, `value`
and `rest` exist so forms can re-open the payment as entered.

What the forms produce (all are the same event type):

| Form | kind | track | in | out |
|---|---|---|---|---|
| Income: "1000 arrived at Anna; Anna 600, Ben 400" | `income` | `true` | Anna 1000 | Anna 600, Ben 400 |
| Expense: "Anna paid 90 for Anna, Ben, Cem" | `expense` | `false` | Anna 30, Ben 30, Cem 30 | Anna 90 |
| Settle up: "Anna pays Ben 400" | `settlement` | `true` | Ben 400 | Anna 400 |

| Type | data | Who |
|---|---|---|
| `payment.created` | payment object above | any claimed member |
| `payment.updated` | payment object + `"base": "<eventId it edits>"` | the payment's creator or admin |
| `payment.deleted` | `{ "id" }` | the payment's creator or admin |

`payment.updated` replaces the whole payment; the last valid update in ledger
order wins. `base` lets clients flag an edit made without seeing the previous
one ("edited concurrently"); it does not change the result. A deleted payment
cannot be updated or deleted again. Arrivals of a deleted payment stop
counting.

### 7.5 Arrivals

| Type | data | Who |
|---|---|---|
| `arrival.recorded` | `{ "id", "payment", "member", "amount" }` | `member` itself; any claimed member if `member` is unclaimed; admin |
| `arrival.removed` | `{ "id" }` | the arrival's author or admin |

The payment must exist, not be deleted and have `track: true`; `member` must
be on its `in` side. Several arrivals per member add up (instalments). An
arrival keeps counting across edits for as long as its member stays on the
`in` side; over-recording is capped (§9).

## 8. Reduction

### 8.1 Procedure

For each event in ledger order:

1. Check `seq` continuity and the hash chain (§6.4).
2. If `id` was already seen in this group, ignore the event (duplicate).
3. Decrypt with the secret of the blob's epoch. No such secret, or failure:
   **invalid** `decrypt`.
4. Parse body. Malformed, `v` ≠ 1 or missing fields: **invalid** `malformed`.
5. Look up the author's key (§8.2). None: **invalid** `unknown_author`.
6. Verify the signature. Failure: **invalid** `bad_signature`.
7. The blob's epoch must be the current epoch (§7.2). Otherwise: **invalid**
   `stale_epoch`.
8. Apply type validation and permissions (§7). Failure: **invalid** with a
   reason code:

   | Code | Meaning |
   |---|---|
   | `forbidden` | the author may not do this (§7 "Who") |
   | `invalid_data` | fields out of range, sums don't match, unknown members, key reuse |
   | `unknown_target` | the member, payment or arrival referred to doesn't exist (or is deleted, or isn't tracked) |
   | `duplicate_id` | an event id, member id, payment id or arrival id that already exists |
   | `misplaced` | `group.created` anywhere but `seq = 1` |
   | `already_claimed` | claiming or renewing a member that is claimed |
   | `bad_invite_sig` | `inviteSig` doesn't verify with the member's current invite key |
   | `bad_recovery_sig` | `recoverySig` doesn't verify with the group's current recovery key |

9. Apply.

`seen.seq` greater than or equal to the event's own `seq` makes the event
**invalid** `malformed`.

An invalid event changes no state. It stays in the history, marked with the
reason, so everyone sees the same thing and who caused it.

### 8.2 Author keys

- `group.created`: `data.admin.key`.
- `member.claimed`, `member.device_claimed`, `member.recovered`: `data.key`
  (the device is claiming).
- every other type: the keys of the claimed member `author`; the signature
  must verify with one of them. Unclaimed members cannot author events.

### 8.3 Roles

The **admin** is the member in `group.created`. Every other claimed member is
a **member**. Unclaimed members are seats others can record payments for.

## 9. Balances

All arithmetic is exact integer arithmetic. Products MUST be computed without
overflow (128-bit intermediate: Swift `multipliedFullWidth`, Go `math/bits`).

### 9.1 Largest remainder

`distribute(T, w)` splits integer `T ≥ 0` over members with integer weights
`w_i ≥ 0`, `W = Σ w_i > 0`:

1. `base_i = floor(T · w_i / W)`, `rem_i = (T · w_i) mod W`
2. `left = T − Σ base_i`
3. sort members by `rem_i` descending, then member id ascending (byte order
   of the lowercase UUID string); give `+1` to the first `left` members.

### 9.2 Per payment

For each payment that is not deleted, with amount `A`:

```
held_h      = in_h                                      if !track
            = min(in_h, Σ arrivals of h for this payment)  if track
R           = Σ held_h
owned       = distribute(R, out)                        (weights = out line amounts)
balance[o] += owned_o            for every out line
balance[h] −= held_h             for every in line
pendingOwned[o] += out_o − owned_o
pendingHeld[h]  += in_h − held_h
```

`balance > 0`: the group owes this member. `balance < 0`: the member owes the
group. Balances always sum to zero. `pendingOwned` is money a member is still
expecting; `pendingHeld` is money still expected to arrive at a member.

### 9.3 Who pays whom

`transfers(balance)`:

1. debtors: members with `balance < 0` (amount `−balance`); creditors:
   `balance > 0`.
2. While both lists are non-empty: sort each by amount descending, then member
   id ascending; the first debtor pays the first creditor
   `min(debtor, creditor)`; subtract; drop members that reached zero.

At most n − 1 transfers. Debts are netted through the group: if A owes B and B
owes C the same amount, the result is A pays C.

### 9.4 Expected

What the balances become once every tracked payment has fully arrived:

```
expected[m]       = balance[m] + pendingOwned[m] − pendingHeld[m]
expectedTransfers = transfers(expected)
```

`expected` sums to zero like `balance`. `expectedTransfers` is the plan
members settle by: settling by `transfers` alone can send money one way that a
pending payment later sends back.

### 9.5 Pay now

How much of each expected transfer can be paid today without depending on
money still on its way: nobody pays money they don't owe yet, and nothing paid
now has to come back, whichever pending payments arrive.

Per payment `p`, its still pending effect on member `m` is
`d_p[m] = (out_m − owned_m) − (in_m − held_m)` (its part of
`pendingOwned − pendingHeld`, §9.2). Assuming each pending payment either
arrives in full or not at all:

```
owes[m] = max(0, −(balance[m] + Σ_p max(0, d_p[m])))   least m can end up owing
owed[m] = max(0,   balance[m] + Σ_p min(0, d_p[m]))    least m can end up owed
for t in expectedTransfers, in order:
    now = min(t.amount, owes[t.from], owed[t.to])
    owes[t.from] −= now
    owed[t.to]   −= now
payNow = the (t.from, t.to, now) with now > 0, in the same order
```

The rest of a transfer (`t.amount − now`) is paid once the money it depends
on has arrived. A settle up that is recorded but not confirmed is a pending
payment like any other, so it is not suggested again. `payNow` is
conservative: it may suggest less than is possible when one member appears in
several transfers.

## 10. Versioning

- The blob version byte (`0x02`, since key epochs) changes only with the
  envelope or crypto.
- `v` in the body changes only for incompatible semantics. New event types and
  new optional fields do not change it.
- Clients MUST NOT write events another client of the same `v` would reject.
